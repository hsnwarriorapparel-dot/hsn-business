- **Gmail STALE-COMPOSE-TAB + HIDDEN-DIALOG BUG (root cause of 'compose-focus-never-ready', 2026-10-31):** TWO independent causes, both fixed in outreach.py `gmail_send`:
(1) **STALE `?compose=` URL PARAM.** A Gmail tab left on `https://mail.google.com/mail/u/0/#inbox?compose=<id>` keeps its compose container inside a `display:none` holder. Clicking Compose does nothing and EVERY send in that tab returns `compose-focus-never-ready` — this is exactly what killed the first 8 leads of the Day-17 wave. FIX: `gmail_send` now picks a CLEAN Gmail tab (no `compose=` in the URL); if only a dirty tab exists it navigates to `#inbox` first. Operationally: **when a Gmail tab is left on a `?compose=` URL, every send from that tab silently fails** — open a fresh tab (`Target.createTarget` → `https://mail.google.com/mail/u/0/#inbox`) and close the dirty one.
(2) **FIRST-DIALOG SELECTOR.** `document.querySelector('div[role="dialog"]')` returns the FIRST dialog, which can be a HIDDEN (0×0) stale compose. The focus-wait loop then reads `height 0` forever and aborts. FIX: select the dialog that is actually rendered (`width > 100 && height > 100`), preferring the one that contains `document.activeElement`.
Diagnostic order when a wave returns `compose-focus-never-ready` for EVERY lead: (a) check `location.href` for `?compose=`; (b) count `div[role="dialog"]` and their sizes (60 hidden 0×0 dialogs = stale-draft pile, purge them); (c) confirm the Compose button exists and the page is not covered by Google's `aloha_frame` feedback iframe (already removed by gmail_send). If SOME leads succeed and others fail with the same error, it is a dead address, not the compose bug.

**Batch-sender return-shape check (silent-death pitfall):** before launching ANY batch send script in the background, run ONE foreground test send and print the raw return of the send function — senders return different shapes (gmail_send returns the string 'sent', NOT {'ok': True}), and a batch whose ok-check calls res.get('ok') on a non-dict dies on lead #1 with the exception swallowed by the loop's try/except. Make the ok-check shape-tolerant: `ok = res.get('ok') if isinstance(res, dict) else ('sent' in str(res).lower())`. Diagnosis rule for a background batch that logs a start line but no action lines: reproduce the FIRST action alone in the foreground and read the raw error — never relaunch blind, and never conclude 'process died mysteriously' before you have run one send by hand.

**Multi-address Email cells from the gmaps scrape (Day-11 bug, 2026-10-25):** the engine's `emails` column can contain a COMMA-SEPARATED list, image-filename pseudo-addresses (`...@2x.png`, `logo-header@2x.jpg`), placeholder domains (`utente@dominio.com`, `contact@mysite.com`, `user@domain.com`), and THIRD-PARTY platform addresses from other sites (`support@schedulista.com`, `info@fitkit.com`, `rgracademy@pec.it`, `soporte@ayudapanel.com`). Correct fix (/home/ubuntu/repair_tighten.py): split the cell, reject only provably-junk candidates (image extensions, `2x`, placeholder domains, hash local parts, platform/third-party domains, PEC-concatenated), then accept a candidate only if (a) its domain matches the lead's OWN website base domain, or (b) it is a webmail address whose local part shares a token with the lead name/website slug. Everything else -> `EXCLUDED (cross-site contamination: ...)`. Always run this BEFORE a wave, then rank the wave by score: site-domain-match 60 > name-matched webmail 30 > other 10, plus business-domain and specific-local bonuses — the top-100 then lands on real gyms instead of webmail dumps.
