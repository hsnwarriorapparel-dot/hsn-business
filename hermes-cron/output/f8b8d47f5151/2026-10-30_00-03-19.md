## Client Reply Playbook (researched 2026-10-17: Kraya WA-B2B study + HubSpot objections + reply-handling skill; full research notes: /home/ubuntu/business-backup/research-whatsapp-b2b-sales.md)

**Qualify conversationally (BANT):** need (what gear for?), timeline (when needed?), budget (qty?), authority (who decides?).
**Proposals in parts, not walls:** (1) restate what they said (2) solution (3) timeline+price (4) ask "works for you?" — each as separate short messages with acknowledgment between.
**Honesty rule (user's correction):** NEVER invent programs/discounts that don't exist. If unsure what client means, ASK them to clarify — a question is better than a fabricated answer.
**Trust signals:** real photos (never AI), specific specs, named clients/countries, 'quality speaks for itself - like the products you saw'.

**Ambiguous replies (like Alvaro's 'content for you guys'):** do NOT assume + do NOT build castles. Two-move response: (1) honest: 'not sure I understood fully' OR reflect their words back as a question, (2) keep the existing offer standing. **Closing micro-steps:** always end with the smallest possible next action (send logo → mockup). Never ask for big commitments.
**System lines in chats:** a "Your security code with <name> changed" line is the CLIENT's own reinstall/phone change — not a security event on our side; ignore it in chat analysis.
**When they ask for better price:** never drop price first. Offer value: higher qty = better rate, or add free logo/belt to the sample.
**Silence after full info:** wait 24-48h, then breakup-lite message. Honor it — no more contact after a breakup message.
**Follow-up drafting standard (user-set):** follow-ups must be business-concrete — specific products, specific prices, and a next step that serves THEIR business (exact quote, side-by-side comparison, real photos, team-size question). ## Model-Provider Health (fix pattern)
- Symptom: fresh sessions (subagents, cron jobs) fail with "Hermes can't reach the model provider" while the CURRENT session keeps working — the running session holds an already-established connection, so only new sessions hit the dead endpoint. Check `hermes config get model.provider` + `model.base_url` first; trycloudflare tunnel URLs are TEMPORARY and die (NXDOMAIN) — an expired tunnel in config silently breaks every fresh session.
- Fix: `hermes config set model.provider <nvidia|openrouter|nous>` + `hermes config set model.base_url <provider's real /v1 endpoint>` + `hermes config set model.default <model that provider serves>`. The config file is write-protected from the agent — always go through `hermes config set`, never patch the YAML directly.
- Verify a provider endpoint before switching: curl its /v1/models URL (expect 200) and resolve DNS — 000/NXDOMAIN means the endpoint is dead regardless of config correctness.
- After any provider switch, fire the morning-briefing cron (action=run) as the canary: it exercises a fresh session end-to-end.
